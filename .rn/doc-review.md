# 文書の書き方とレビューの観点

README・設計書・ガイドを書くときと、書いたあとに1回だけ回すレビューで、同じこの文書を拠りどころにする。見出しの型は持たない。見出しは、文書ごとの読む人と、読んだあとにできることから組み立てる。枠があると、要らない中身まで埋めてしまうから。

必ず入れるもの: README には手に入れて開くまでの手順と License、設計書には確かめていない仮定。

## 3つの文書の役目

README と設計書は、目指す姿を伝える文書で、実装はこの2つをゴールにして作る。

- README: ユーザーに、ベネフィットと使い方を伝える
- 設計書: 開発者に、それをどう実現するかを伝える
- ガイド: README の使い方のうち、手を動かすための詳しい手順を別のファイルにしたもの。README と同じくユーザーに向けた、目指す姿の一部

依存の向きは README → 設計書 → 実装（README → 実装、ガイド → 実装も）。変えるときは上から変える。実装が変わっても README と設計書は変わらず、変わるなら README か設計書が先に変わり、実装がそれに従う。

文を書くかどうかは、「実装が従うべき目指す姿か」で決める。README と設計書を満たす限り実装が自由に選んでよいこと（コードの分け方、関数やファイルの名前、内部のデータの形）は書かない。

## README の観点

読む人: Figma で LP / HP を作るデザイナーで、Telldes を初めて知った人。上から一度読む。読んだあと、自分に何をしてくれるかが分かり、使うかを決め、使い始められる。

1. ベネフィットが最初に伝わる: 何が楽になり、何が起きなくなるかが、冒頭で分かる
2. 目指す姿で書いている: 今の試作や未実装の状態でなく、完成した Telldes を使う体験になっている
3. 使い方の流れが一目で分かる: デザインしてから CC がページを作るまでの段が、それぞれで何をし何を得るかとともに見える。手を動かす細かい手順はガイドへ
4. 実装の都合が無い: 実装を作り直しても書き換えずに済む。書き換わるなら、それは README が先に変わるべき決定か、書かなくてよいこと
5. 理由を持ち込まない: なぜこの形かは設計書へリンクする
6. 事前の知識なしで読める: 言葉は初めて出たところで分かる。読み手に Figma の基本以上を求めない

## 設計書の観点

読む人: Telldes を作る人・直す人（人と CC）。上から一度読み、変えたくなったときに戻ってくる。読んだあと、README の姿をどう実現するかが分かり、ある変更がこの設計に合うか、合わないならなぜかを言える。

1. 位置づけを最初に言い切る: README の姿をどう実現するかの文書であり、実装と食い違ったらこちらが正しい
2. 守ることは数個で、1つずつ言い切る: 1文の主張のすぐ後に、外すと何が起きるかを書き、README の姿か前提までつなげる。理由を別の箇条に切り離さない
3. 仕組みの骨組みがある: 直す人が問う順に、誰が何をし何を決めるか（役目と境目）、どんな状態があり操作でどう動くか、何で判断するか（決まりの一覧ではなく、分ける基準）、何が残り誰が書き誰が読むか
4. 壊してはいけない約束を名指ししている
5. 代償と選ばなかったやり方がある: 何を諦めたか、ほかのやり方をなぜ取らないかが分かる
6. 名前は、使う人に見える名前と外との約束（Figma のファイルに残すもの、zip）だけ: コードのファイルや関数の名前を出さない
7. 見出しだけで筋が追える: 見出しは直す人の問いか主張になっている
8. 表は、いくつかのものを同じ欄で並べて比べるときだけ: 筋道は文章で書く
9. 事実・仮定・決定が分かれている: 確かめていない事実は仮定として書く
10. 経緯が無い: いつ・なぜ直したかは git にある

## ガイドの観点

読む人: Telldes を使うと決めたデザイナーで、Figma を開いて今から作る人。手順を追いながら読む。読んだあと、CC に渡せる zip を作れる。

1. 順番どおりに追える: 手順ごとに、すること・その結果どう見えるかがある
2. 例がある: よい作り方とよくない作り方を、図や表の例で見せる
3. 渡らないもの・止まるものが、それに関わる手順の中で分かる
4. 最後に、できたかの確かめ方とよくあるつまずきがある
5. 理由は設計書へリンクし、持ち込まない
6. 実装の都合が無い: 画面の言葉や手順は、実装が従う目指す姿として書く

## 回し方

1. 文書ごとに、前の経緯を知らないエージェントを1つ立てる。渡すのは、その文書と、この文書の「3つの文書の役目」とその文書の観点だけ（書いた過程・前の版・steering は渡さない）
2. その読む人として上から読ませ、報告させる: 目的を果たせたか、見出しだけで筋が追えるか、どこでつまずいたか、要らなかったものは何でそれは誰のためのものか、観点ごとの OK / NG
3. 指摘を分ける
   - 書き方の問題: 直す
   - 中身の問題（規則に穴がある、2つの主張が食い違う）: 文章でごまかさず、ユーザーに出す
   - 形の問題（役目の違う中身が混ざっている）: 置き場所を移す
4. レビューは1回。直したら結果をユーザーに見せ、次は指示を受けてから
