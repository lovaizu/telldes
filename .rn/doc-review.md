# README と設計書の書き方とレビューの観点

README と設計書を書くときと、書いたあとに1回だけ回すレビューで、同じこの文書を拠りどころにする。見出しの型は持たない。見出しは、読む人と、読んだあとにできることから組み立てる。枠があると、要らない中身まで埋めてしまうから。

## 2つの文書の役目

README と設計書は、目指す姿を伝える文書で、実装はこの2つをゴールにして作る。

- README: ユーザーに、ベネフィットと使い方を伝える。使い方の詳しい手順は別のファイルに分けてリンクしてよく、そのファイルも README の一部として同じ観点で見る
- 設計書: 開発者に、README の姿をどう実現するかを伝える

依存の向きは README → 設計書 → 実装（README → 実装も）。変えるときは上から変える。実装が変わっても README と設計書は変わらず、変わるなら README か設計書が先に変わり、実装がそれに従う。

文を書くかどうかは、「実装が従うべき目指す姿か」で決める。README と設計書を満たす限り実装が自由に選んでよいこと（コードの分け方、関数やファイルの名前、内部のデータの形）は書かない。

## README の観点

読む人: その製品を初めて知ったユーザー。上から一度読む。読んだあと、自分に何をしてくれるかが分かり、使うかを決め、使い始められる。

1. ベネフィットが最初に伝わる: 何が楽になり、何が起きなくなるかが、冒頭で分かる
2. 目指す姿で書いている: 今の試作や未実装の状態でなく、完成したものを使う体験になっている
3. 使い方の流れが一目で分かる: 始めてから結果を得るまでの段が、それぞれで何をし何を得るかとともに見える
4. 実装の都合が無い: 実装を作り直しても書き換えずに済む。書き換わるなら、それは README が先に変わるべき決定か、書かなくてよいこと
5. 理由を持ち込まない: なぜこの形かは設計書へリンクする
6. 事前の知識なしで読める: 言葉は初めて出たところで分かる。読み手に、その製品を使う前から持っている知識以上を求めない
7. 手に入れて使い始めるまでの手順と、License がある

## 設計書の観点

読む人: その製品を作る人・直す人（人と AI）。上から一度読み、変えたくなったときに戻ってくる。読んだあと、README の姿をどう実現するかが分かり、ある変更がこの設計に合うか、合わないならなぜかを言える。

1. 位置づけを最初に言い切る: README の姿をどう実現するかの文書であり、実装と食い違ったらこちらが正しい
2. 守ることは数個で、1つずつ言い切る: 1文の主張のすぐ後に、外すと何が起きるかを書き、README の姿か前提までつなげる。理由を別の箇条に切り離さない
3. 仕組みの骨組みがある: 直す人が問う順に、誰が何をし何を決めるか（役目と境目）、どんな状態があり操作でどう動くか、何で判断するか（決まりの一覧ではなく、分ける基準）、何が残り誰が書き誰が読むか
4. 壊してはいけない約束を名指ししている
5. 代償と選ばなかったやり方がある: 何を諦めたか、ほかのやり方をなぜ取らないかが分かる
6. 名前は、使う人に見える名前と外との約束（保存する形、渡す形）だけ: コードのファイルや関数の名前を出さない
7. 見出しだけで筋が追える: 見出しは直す人の問いか主張になっている
8. 表は、いくつかのものを同じ欄で並べて比べるときだけ: 筋道は文章で書く
9. 事実・仮定・決定が分かれている: 確かめていない事実は仮定として書く
10. 経緯が無い: いつ・なぜ直したかは git にある

## 回し方

1. 文書ごとに、前の経緯を知らないエージェントを1つ立てる。渡すのは、その文書と、この文書の「2つの文書の役目」とその文書の観点だけ（書いた過程・前の版・作業の記録は渡さない）
2. その読む人として上から読ませ、報告させる: 目的を果たせたか、見出しだけで筋が追えるか、どこでつまずいたか、要らなかったものは何でそれは誰のためのものか、観点ごとの OK / NG
3. 指摘を分ける
   - 書き方の問題: 直す
   - 中身の問題（決まりに穴がある、2つの主張が食い違う）: 文章でごまかさず、ユーザーに出す
   - 形の問題（役目の違う中身が混ざっている）: 置き場所を移す
4. レビューは1回。直したら結果をユーザーに見せ、次は指示を受けてから
