# 文書の書き方とレビューの観点

README・設計書・ガイドを書くときと、書いたあとに1回だけ回すレビューで、同じこの文書を拠りどころにする。見出しの型は持たない。見出しは、文書ごとの読む人と、読んだあとにできることから組み立てる。枠があると、要らない中身まで埋めてしまうから。

必ず入れるもの: README には手に入れて開くまでの手順と License、設計書には確かめていない仮定。

## 3つの文書の役目

README と設計書には、Telldes の変わらない土台を書く。一度決めたらめったに変わらず、画面や実装を作り直しても書き換えなくてよいこと。迷ったときに立ち返る道標になる。

- README は UX の土台: 誰が、何のために、どんな流れで使い、何を得るか。できあがった姿で書く
- 設計書は仕組みの土台: その UX を支える基本の考え方と、それを選んだ理由と払った代償
- ガイドは、デザイナーが今 Figma で手を動かすための手順。画面や実装に合わせて直す文書で、細かい決まりはここに置く

文を書くかどうかは次の2つで決める。

- これが変わったら Telldes の形が変わるか。変わるなら、README か設計書に書く
- 画面や実装を作り直したら変わりうるか。変わりうるなら、README と設計書には書かない。ガイド・画面・コード・テストが持つ

例: 「Review は、出力が壊れるときだけ止める」は設計書に書く。「Dark support ON で、Light か Base につないでいない色は error」はその帰結なので、コードとテストが持ち、デザイナーに要るならガイドに書く。

## README の観点

読む人: Figma で LP / HP を作るデザイナーで、Telldes を初めて知った人。上から一度読む。読んだあと、自分に何をしてくれるかが分かり、使うかを決め、次にガイドへ進める。

1. 得るものが最初に伝わる: 何が楽になり、何が起きなくなるかが、冒頭で分かる
2. できあがった姿で書いている: 今の試作や未実装の状態でなく、完成した Telldes を使う体験になっている
3. 流れが一目で分かる: デザインしてから CC がページを作るまでの段が、それぞれで何をし何を得るかとともに見える
4. 変わらないことだけ: 画面の部品の並び・ボタンの置き場所・規則の一覧・欄の細部・zip のファイルごとの中身が無い。画面を作り直しても書き換えずに済む
5. 役目を越えない: 作り方はガイドへ、理由は設計書へリンクし、中身を持ち込まない
6. 事前の知識なしで読める: 言葉は初めて出たところで分かる。読み手に Figma の基本以上を求めない

## 設計書の観点

読む人: Telldes を直す人（人と CC）。上から一度読み、変えたくなったときに戻ってくる。読んだあと、ある変更が土台に合うか、合わないならなぜかを言える。

1. 土台だけ: 各考え方は、変えたら Telldes の形が変わるもの。1つの機能だけの規則・既定値・欄の名前・error の一覧は無い（考え方を示す例として1つ出すのはよい）
2. 数が少ない: 全体を形づくる考え方は数個。増えたら、帰結を土台と取り違えていないか疑う
3. 理由が目的までつながる: 選んだこと → 理由 → 目的か前提、が文章で途切れずにつながる。理由を箇条に切り離さない
4. 代償と退けた道がある: 何を諦めたか、ほかのやり方をなぜ取らないかが分かる
5. 事実・仮定・決定が分かれている: 確かめていない事実は仮定として書く
6. 経緯が無い: いつ・なぜ直したかは git にある

## ガイドの観点

読む人: Telldes を使うと決めたデザイナーで、Figma を開いて今から作る人。手順を追いながら読む。読んだあと、CC に渡せる zip を作れる。

1. 順番どおりに追える: 手順ごとに、すること・その結果どう見えるかがある
2. 例がある: よい作り方とよくない作り方を、図や表の例で見せる
3. 渡らないもの・止まるものが、それに関わる手順の中で分かる
4. 最後に、できたかの確かめ方とよくあるつまずきがある
5. 理由は設計書へリンクし、持ち込まない

## 回し方

1. 文書ごとに、前の経緯を知らないエージェントを1つ立てる。渡すのは、その文書と、この文書の「3つの文書の役目」とその文書の観点だけ（書いた過程・前の版・steering は渡さない）
2. その読む人として上から読ませ、報告させる: 目的を果たせたか、見出しだけで筋が追えるか、どこでつまずいたか、要らなかったものは何でそれは誰のためのものか、観点ごとの OK / NG
3. 指摘を分ける
   - 書き方の問題: 直す
   - 中身の問題（規則に穴がある、2つの主張が食い違う）: 文章でごまかさず、ユーザーに出す
   - 形の問題（役目の違う中身が混ざっている）: 置き場所を移す
4. レビューは1回。直したら結果をユーザーに見せ、次は指示を受けてから
