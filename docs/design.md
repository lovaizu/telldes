# Telldes 設計書

## 1. 目的と背景

### 1.1 何を目指すか

デザイナーが Figma で作り方に従ってデザインするだけで、Claude Code（CC）がデザインカンプと同じ見た目のコードを書ける状態。デザイナーは zip を書き出して CC に渡すだけで、CC への指示も zip に入っている。

### 1.2 これが無いと何が起きるか

CC にカンプの画像だけを渡すと、次のことを CC が画像から当てることになり、外れて手戻りになる。

- 背景と中身の区別
- 色・大きさ・間隔の正確な値
- 見出しのレベル（h1 / h2 / h3）
- 並べ方の意図（どこが伸び、どこが固定か）
- 動き（sticky・スクロール・カルーセルなど）

### 1.3 達成に何が要るか

- 出力の正確さを何より優先する。出力が不正確なら、CC のコードもそのまま不正確になる。便利さや実装の手間は、正確さと引き換えにしない
- デザイナーが普段の作り方のまま使えること。作り方は Figma 公式のやり方をそのまま土台にし、telldes 独自の約束は、公式のやり方では表せないことだけに限る。覚えることが増えるほど守られず、忘れられる
- CC が何も当てなくて済む出力。当てる必要がある時点で、出力の設計が足りていない。そのために出力は次の4つを守る
  - 形が揃っている: 同じ種類のものは同じ形で出る。特別扱いを作らない
  - 1か所にだけある: 同じ事実を2か所に書かない。片方だけ古くなる形を作らない
  - 欠けていると分かる: 黙って落とさない。落としたなら落としたと書く
  - 推測させない: 宣言されていないことは出さない。値から意図を当てにいかない

### 1.4 やらないこと

- 描かれていないものを補うこと。カンプに無い幅での振る舞いや、描かれていない状態（hover など）を telldes が推測して足すことはしない。必要ならデザイナーが描くか、書き出しの設定やレイヤーごとの補足（note）に書く
- 状態（hover・disabled など8種）の専用の受け口。今は書き出しの設定にある自由記述の欄で受ける。専用の受け口は後で決める
- 有料プランを前提にすること。Figma Free で成り立つ形にする（2.2）

## 2. 前提と制約

### 2.1 何を前提にするか

- デザイナーは1人で、作るのは LP / HP。共同編集は要らない
- 受け取るのは CC。zip の中身だけを読んで作業する
- Figma のレイヤーの並び（Auto Layout）は、CSS の flexbox に一対一で写せる

### 2.2 何に縛られるか

- Free では1つのコレクションに複数のモードを作れない → ライトとダークを別のコレクションに分ける（4.4）
- Free ではライブラリを公開できず、ファイルをまたいで変数を共有できない → トークン一式はプラグインがファイルごとに作る（4.3）
- Free にはアノテーションが無い → 補足はプラグインの note で受ける
- Free では非公開のプラグインを配れない → Figma Community に公開する
- Starter のチームのファイルは3ページまで → Drafts で作る（ページ数に上限が無い。共同編集できないのは 2.1 のとおり問題にならない）
- プラグインは今開いているページしか見ない。書き出せる形式は PNG / JPG / SVG / PDF だけ → 画面でないもの（部品置き場・favicon 用など）は別のページに置いてもらう。ICO は PNG を包んで作る

## 3. 全体の考え方

### 3.1 中心の考え方は何か、なぜそれで解けるか

「当てる」を「宣言を読む」に置き換える。1.2 の困りごとは、どれも CC が画像から当てていることから起きる。背景か中身か、どこが伸びるか、どの色がどの役割か — これらを Figma の普段の機能（Auto Layout・変数・スタイル・レイヤー名）で宣言してもらい、telldes はそれを読んで、CC がそのまま使える形にして渡す。宣言が無いところは、当てずに「無い」と伝える。

### 3.2 どんな部品があり、それぞれ何を受け持つか

- 制作ルール（README）: 何をどう宣言すればよいかをデザイナーに伝える
- プラグイン: 宣言の抜けや矛盾を見つけて知らせる（チェック）。トークン一式を用意する（Setup）。補足を受ける（note）。ライト・ダークを切り替える。zip を書き出す
- zip: CC への依頼書。CC はこれだけで作業できる

デザインの判断はプラグインが Figma の上で受け、実装の判断は zip の中の `steering.md` で CC が受ける。分ける基準は「誰が答えられるか」。デザイナーは Figma を開いている今が一番答えやすく、zip を受け取った人がデザイナーとは限らない。レスポンシブの切り替え幅やページの題名・OG 画像のような、デザイナーが答えられるものはプラグインの Export 設定で受け、CC に聞き直させない。

### 3.3 どう流れるか

```
デザイン → チェック → 書き出し → zip を CC に渡す
```

チェックは書き出しの前に必ず走り、出力が壊れる違反があれば書き出さない（4.7）。チェックの結果は3種類に分ける。

- error: 直さないと出力が壊れるもの。書き出しを止める。Figma の画面に出る
- 付け忘れの知らせ: 出力は壊れないが、宣言し忘れたと機械的に分かるもの。止めない。Figma の画面に出る
- 含まれなかったもの: telldes が扱わないもの（違反ではない）。Figma の画面と zip の README に出る

書き出すものとチェックするものは、同じ時点に読んだ同じデータから作る。別々に読むと、チェックしたものと渡したものがずれうるから。

## 4. 仕組みごと

### 4.1 レイヤー構造 — HTML の構造を当てさせない

守ること: Figma のレイヤーの木が、そのまま HTML の要素の木になる。

- ページ直下のフレームを1画面、その直下をセクションとし、ページ／セクション／ブロック／エレメントの4階層で表す。CC はページの構造を当てずに済む
- 子を持つフレームには Auto Layout を必須にする。Auto Layout は flexbox に一対一で写せるが、自由配置は写し方が決まらない。内部を自由配置したい装飾は Group にまとめれば通す（逃げ道）
- 大きさの決め方は Hug / Fill / Fixed と最小・最大だけ。どれも CSS への写し方が1つに決まる
- 背景はフレームの塗りだけで表す。背景用の子レイヤーを許すと、CC が「背景か中身か」を画像から当てることになる
- 名前は同じ親の中で重ならなければよい。階層はレイヤーの木が持っているので、名前に親を繰り返させない
- 見出しレベルやランドマークは、決まったレイヤー名（`heading`・`nav` など。一覧は README）から CC が決める。デザイナーに HTML を意識させないため

破られたら: Auto Layout の無いフレーム・大きさの決め方が写せないものはチェックの error になる（4.7）。

### 4.2 トークン — 値の役割を当てさせない

守ること: デザイナーが名前を付けた値は、CC にもその名前で届く。名前の無い値は、値のまま正しく届く。

- トークンの元は Figma の現行の作法に合わせる。色・数値・書体は変数、文字の組み合わせは Text Style、単色にできない塗り（グラデーション・複数の塗り）は Color Style、影は Effect Style。単色の Color Style は Figma 自身が変数を勧めているので元にせず、使われていたら「含まれなかったもの」として伝える
- 変数を使うかどうかはデザイナーに任せ、促さない。使わなくても値は正しく届き、出力は壊れないから。例外は、既にあるトークンと同じ値なのにそれを指していない箇所で、付け忘れとして知らせる
- 名前は自由。telldes は値から役割を当てにいかない（誤りのもとになる）。そのかわり共通の語彙（README）を用意する。共通にするのは名前だけで、値はデザインごとに違ってよい
- CSS 変数名は telldes が決めて `tokens.json` に書く。CC に組み立てさせると組み立て方を当てることになり、Dev Mode でデザイナーが見ている名前ともずれうる。変数に Figma の code syntax（WEB）があればそれを使い、無ければ Figma と同じく名前から作る
- CSS に書く値（単位つき）も telldes が決めて書く。`16` が `16px` か `16` かは CC には決められない
- `tokens.json` は W3C の Design Tokens の形を骨組みにするが、準拠はしない。骨組みは広く知られた形に乗る一方、値の書き方は CSS にそのまま写せる形を優先する
- 名前で意味を宣言できるトークンは1つだけ — `radius/full`。円やピルは Figma では px の値でしか現れず、`9999px` と px 値のどちらが意図かは値から決まらない。そこでこの名前へのつながりを「常に丸める」という宣言として読む。丸い形なのにつながっていなければ付け忘れとして知らせる

破られたら: 対象外のものを使っていれば、書き出した zip の README と画面に「含まれなかったもの」として出る。値を決められなかったもの（単位など）も同じく伝える。

### 4.3 Setup — トークン一式をファイルに用意する

守ること: Setup を実行したファイルには、共通の語彙どおりの変数とスタイルがそろい、telldes がそのまま正しく読める設定になっている。

- 作るのは、変数（ライト・ダーク・共通の3コレクション）と、Text Style・Effect Style。Free ではファイルをまたいで共有する手段が無いので（2.2）、プラグインが作るしかない。数が多く、手で作らせると下の設定を漏らす
- 値は仮置き。満たすのは、隣り合う段階・役割どうしの違いが目で分かることだけ。デザインごとに値は変えてよい（4.2）
- ダーク用の色も最初から作る。カラーピッカーから隠れているので、ダーク対応しないファイルでも邪魔にならない。ダークを始めるときは色を入れるだけで済む
- 変数ごとに、使える欄を絞る（色は塗り・文字・線・影のどれか、余白は間隔、など）。合わない欄のピッカーに出さないため。書体の変数は、この絞り込みが「書体である」という印も兼ねる
- 変数ごとに CSS 変数名を書いておく。Dev Mode でデザイナーが見る名前と、CC が使う名前をそろえるため（4.2）
- スタイルの中の色と書体は変数につなぐ。つながっていないと、ダーク対応を ON にした時点で Setup 自身が作った影が error になる
- 何度実行しても増えない。あるべき一式と今あるものの差だけを作る・直す。「今どこまであるか」を気にせず押せるようにするため
- 作ったあとの名前や値の変更は Figma の標準の画面で行う。telldes は編集の画面を持たない。同じものを直す場所を2つにしない
- Setup を使わなくてもよい。普段の作法で作ったファイルも、そのまま読めて正しく出る

破られたら: あるべき一式と今あるものの差は Figma に触らない部分で計算するので、テストで確かめる（4.9）。実際にできた変数・スタイルと、2回目で何も増えないことは実機で確かめる。

### 4.4 ダークモード — 1つのフレームで切り替える

守ること: ダーク対応を宣言したファイルでは、CC にライトとダークの両方の値と見た目が届く。

- 変数はライト・ダーク・共通の3つのコレクションに分ける。Free ではモードを作れないが、コレクションの数には制限が無い。テーマで変わるのは色だけなので、対を持つのは色だけにし、余白や角丸は共通に置く
- 変数名にテーマを入れない。`bg-light` にすると CSS 変数名も分かれ、同じ `--bg` がテーマで値を変える形を CC が作れない
- ダーク用のフレームを複製しない。telldes が変数のつながりをライト⇄ダークで付け替えて、キャンバスの上で実際にダークを描く。複製すると、同じページが別ページとして CC に渡り、ライトの変更がダークに伝わらず、作り直すたびに Figma のコメントが迷子になる
- 付け替えはページ全体とスタイルにかける。ダークはサイト全体の振る舞いで、フレームごとに明暗が混ざる状態は実物に無い。影とグラデーションの色も付け替える。変わらなければダークの画像が実物と食い違う
- ダーク対応するかは Export 設定で宣言する。Setup は全ファイルにダークのコレクションを作るので、その有無では判断できない
- ダーク用の色を手で選べないようにする。ダークの変数はカラーピッカーから隠し、telldes だけがつなぎ替える。色の値の編集はデザイナーの仕事なので開けておく

代償: ファイルが「今どちらのテーマか」という状態を持つ。書き出しは「ライトにして読む → 撮る → ダークにして撮る → ライトに戻す」になり、途中で失敗しても必ずライトに戻す。それでもダークで残った場合（強制終了など）は、次に開いたときに戻すよう促す。キャンバス上でライトとダークを並べて比べることはできない。

破られたら: ダーク対応のファイルで、色が変数につながっていない箇所（ライトのまま取り残される）や、ライトの状態なのにダークの変数につながっている箇所は、チェックの error になる。

### 4.5 レスポンシブ — 描かれていない幅を当てない

守ること: CC は、デザイナーが描いた幅と宣言した切り替え幅だけでメディアクエリを作る。

- 幅ごとの見た目は別のフレームで描く。他の画面と同じ仕組みに乗り、違いはレイアウトだけになる
- 切り替える幅とコンテンツの幅は Export 設定で宣言する。フレームの幅と切り替える幅は一致しない（1440px のデザインを 1440px から使うと、1439px ではスマホ版が出る）。また、1440px のフレームの左右の大きな余白が「ただの余白」か「コンテンツ幅を作るためのもの」かは、1440px ではどちらも同じ見た目になり、データからは決まらない。宣言があれば推測は要らない
- 宣言が無ければ、フレームは1つの幅として出る

### 4.6 CC に渡す形 — 同じ見た目を当てずに書ける

守ること: CC は `spec.json` と `tokens.json` の値をそのまま書けば、カンプと同じ見た目になる。書けないものは、書けないと分かる。

- 値はいつも解決済みで出し、トークンを使っていればその名前も添える。トークンを使っていないファイルでも正しく作れ、使っていれば CC は `var()` で書ける
- Figma の値を CSS の値に直すのは telldes の仕事。Figma と CSS で基準が違うもの（グラデーションの向きと位置、画像の置き方、自由配置の子の位置、影を落とすプロパティなど）を CC に直させると、直し方を当てることになる
- CSS で同じに描けないものは、Figma に描かせた画像で渡す。特殊なグラデーション・破線や複数の線・加工した画像の塗りなど。CSS で近いものを作らせれば推測になり、伝えるだけにすれば描かれない。Figma 自身の描画ならそのものになる
- それでも描けないものは出さずに伝える。出して誤って描かせるより、描けなかったと分かる方がよい
- 非表示のレイヤーは出さずに伝える。描かれていないものを CC に作らせると、カンプと食い違う
- 1つのテキストの中の部分的な違い（一部だけ太字・リンクなど）も出す。代表の値だけで出すと黙って消える
- ファイル名とパスは telldes が決めて `spec.json` に書く。CC に組み立てさせない。重なる名前には番号を付け、大文字小文字だけの違いも別名として扱う（macOS や Windows では同じファイルになり、片方が黙って上書きされるため）
- 補足（note）は自由記述のまま渡す。形を決めると、デザイナーが書けることを狭める。解釈は CC に任せる。全体に効く補足は Export 設定の共通ルールで受け、note と食い違えば狭い方（note）を採る

破られたら: 形が崩れていないことはテストで確かめる（4.9）。CC がその形から同じ見た目を書けるかは、zip を CC に渡して実物で確かめる。

### 4.7 チェック — 出力が壊れるものだけを止める

守ること: 書き出しを止めるのは、そのまま渡すと出力が壊れるものだけ。それ以外は止めずに伝える。

チェックの置き場所と重さは次の3つで決める。新しいチェックを足すときも個別に考えず、ここに当てる。

- error は、デザイナーが選んだやり方との食い違いだけを見る。やり方そのものは強制しない。「変数を使え」は error にしない。たとえばダーク対応を宣言したファイルでだけ、テーマの食い違いを error にする
- 1行は、デザイナーが下す1つの判断。原因ごとにまとめる。同じ色が30か所で変数につながっていなくても、判断は「この色を変数にする」の1回なので1行にする
- チェックは書き出しの前に自動で走り、結果は必ず画面に出す。

- チェックの範囲は、書き出す範囲と同じ。zip に入らないものが壊れていても出力は壊れない。範囲の決め方を1か所に置き、チェックと書き出しの対象がずれないようにする
- 変数を使わず値のまま作ったことは、どこにも伝えない。値のままでも正しく届くので直す理由が無く、並べると本当に落としたもの（含まれなかったもの）が埋もれる
- 書き出しの途中でダークのまま残ったことは、error ではなく「ライトに戻しますか」の促しにする。違反ではなく、中断で残った状態だから

破られたら: 見本のファイルにわざと入れた違反・付け忘れ・含まれなかったものが、すべて出て、それ以外は出ないことをテストで確かめる（4.9）。

### 4.8 画面 — 機能ではなく、デザイナーが気にするもので並べる

守ること: 直すべきことは、直す相手（トークン・画面・レイヤー）のところに出る。

- 画面はデザイナーの関心の対象で組む（オブジェクト指向 UI）。以前は機能ごとのタブ（Setup / Review / Notes / Export）で、同じレイヤーの違反と note が別々のタブに入り、「知らせは書き出しのタブに出るのに、直す作業は別のタブ」といったずれが生まれていた。持ち主のところに戻せば、ずれは原因ごと消える
- ビューは3つ — トークンの一覧（語彙）、画面の一覧（渡すもの。末尾に「渡されないもの」）、選んだレイヤーの詳細。どれに出すかは、デザイナーの1つの判断の対象が何かで決まる
- Setup だけは機能として置く。対象が今のファイル1つに決まっていて、選ぶ必要が無いから
- テーマの現在の状態・error の数・付け忘れの数は、いつも見えるところに置く。telldes はファイルの状態（テーマ）を書き換えるので、知らせずに変えない。まだ数えていない数を 0 と見せない
- 書き出しは確認のビューを通す。並びは「設定 → 共通ルール → 付け忘れの数 → 実行」。チェックのゲートは「実行」にかけ、確認のビューの入口にはかけない。入口にかけると、error を消すために設定（ダーク対応の ON/OFF など）を直しに行けなくなる
- Export 設定の専用欄は、CC が値としてそのまま使うものだけにする。切り替え幅・ON/OFF・`lang`・meta の中身など。それ以外は共通ルールの自由記述で受ける。項目が増えても振り分けに迷わない
- 設定が指すフレームは名前ではなく id で持つ。名前を変えただけで参照が黙って切れるのを防ぐ。切れていたら確認のビューで知らせる
- 密度・アイコン・最初に開いておく場所は、実機で使って決める。紙の上では決まらない

### 4.9 作りとテスト — 約束を Figma なしで確かめる

守ること: CC に渡すものの形・チェックの規則・テーマの付け替えの計算が、テストで丸ごと確かめられている。

- コードは3つの層に分ける — Figma から読む層、読んだデータから出力とチェック結果と付け替えの計画を作る層、画面。約束（形・規則・計算）はすべて真ん中の層に置く。真ん中の層は Figma に触らないので、テストで確かめられる。Figma に触る層は実機でしか確かめられないので、判断を持たせず薄くする
- テストは約束だけを確かめる。コードの作りを確かめるテストは、作りを変えるたびに書き直しが要るうえ、CC に渡るものの正しさについて何も言わない
- 入力は実物の見本ファイルから取る。手で作った入力は、Figma が実際に返す形と食い違いうる。食い違うところこそ出力が壊れるところ
- 結果は正解と丸ごと比べる。一部だけを見るテストは、見ていないところが崩れても通る
- 正解は今の出力を写して作らない。写せば、今の出力を正解と呼ぶだけになる。正解は `prompt.md` の取り決めと見本に入れたものの一覧に照らして作る
- Figma でしかわからないことはテストで真似ず、実機で確かめる。真似が実物と違えば、壊れていても通るテストになる。テストが走る環境（Node）とプラグインの環境の違いも、テストでは原理的に見つからない

## 5. ほかの案と代償

### 5.1 なぜこの形で、ほかの形ではないのか

捨てた案と、その理由。

- 画像だけを渡し、CC の読み取りに任せる: 1.2 の困りごとそのもの
- telldes が値から意図を当てる（大きな余白をコンテンツ幅に、短辺の半分の角丸を丸に、など）: 当てたものは外れうる。外れても誰も気づかない。宣言を読む方が確実
- ダーク用のフレームを複製する: 4.4 のとおり、同じページが別ページとして渡り、古さを揃える仕組みが別に要る
- Figma の変数のモードでライト・ダークを持つ: Free では使えない
- グラデーションを1つのトークンにする: stop の位置はノードの縦横比でずれる。1つの CSS 変数では同じに描けない
- W3C の Design Tokens に完全に準拠する: 値の書き方が CSS に写しにくく、CC が変換を当てることになる
- 機能ごとのタブで画面を組む: 4.8 のずれを生んでいた
- 手で作った入力でテストする: 4.9 のとおり、Figma の実際の形との食い違いを確かめられない

### 5.2 何を諦めたか

- ファイルがテーマの状態を持つ。中断でダークのまま残りうる。戻す手順と、開いたときの促しで受ける
- キャンバスでライトとダークを並べられない。比べるのは書き出した画像で行う
- Free の範囲で閉じるため、Drafts で作る前提になる。共同編集はできない
- CSS 変数名の重なりは確かめない。主な原因（変数とスタイルの同名、`.` を消すことによる重なり）は名前の作り方で起きなくしており、残るのは紛らわしい名前を両方作ったときだけで、まれだから
- Dev Mode が見せる CSS 変数名と、telldes が作る名前が違うことがありうる。Figma の資料で大文字の扱いが決まらないため。CC は `tokens.json` の名前だけを使うので、出力は壊れない
- 描けないものは描かない。近い見た目を作らせるより、描けなかったと伝える方を選んだ
